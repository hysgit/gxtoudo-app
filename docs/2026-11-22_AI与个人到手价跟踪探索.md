# AI 对话与个人到手价跟踪：功能探索

日期：2026-11-22。范围是技术可行性与接入方案，尚未实现功能、调用模型、登录电商账户或创建价格监控。

## 结论

AI 数据助手可以在现有 Java 后台实现，Flutter 负责对话输入、结果展示和跳转原记录。模型通过受权限约束的查询与计算工具访问已同步的数据；不依赖将全部记录一次性塞入提示词。金额和统计结果由程序计算，再交给模型解释。

京东、淘宝的个人价格跟踪有可验证的实现路线，但目前不能承诺对任意商品持续获得与手机端相同的最终到手价。需要先用本人账户和指定 SKU 验证取价渠道、个人优惠覆盖、登录态有效期以及平台允许的访问方式。公开商品价或推广价不能默认充当个人到手价。

后台降价通知需要新增远程推送。现有 iOS 实现是本地日历触发通知，不是已接通 APNs 的服务端通知链路。

## 一、后台 AI Agent

### 用户流程

在 App 内打开 AI 对话，发送“本月餐饮花了多少”“哪些任务逾期了”“把便签里提到装修的内容汇总一下”等请求。后台判定需查询的记录、执行相应工具、汇总证据，再通过流式响应显示结果。结果附任务、账单或便签的可打开引用，并注明统计区间、筛选口径和数据时间。

较长分析保存成后台会话任务；页面断开后，可以重新连接查看状态与结果，不要求 App 始终保持前台。它首先是用户发起的查询助手，不自动修改任务、账单或便签。

### 最小实现

- 模型配置：后台保存兼容接口地址、模型名和 API Key。确认该服务支持 `/v1/chat/completions`、工具调用及所需流式格式；“兼容”不能代替一次真实连通性与工具调用测试。模型若不支持工具调用，需要单独评估适配方式。
- Agent 调度：先认证，再用短事务读取必要数据，释放连接后调用模型；工具查询按需分页。设置单次工具调用数、耗时与 token 预算，避免无界循环。
- 数据工具：`query_tasks`、`query_notes`、`query_bills`、`aggregate_bills`、按 ID 获取原记录。工具参数限定日期、状态、空间、关键词和分组字段；不让模型直接执行任意 SQL 或系统命令。
- 精确计算：财务聚合采用 BigDecimal；任务数量、完成率、逾期天数等由确定性程序计算。需要一般算术时使用限定操作的十进制计算工具。模型负责选择工具和解释结果。
- 会话：保存用户问题、工具结果摘要、引用与最终回答；历史对话重新读取原记录时仍检查当前权限与删除状态，不能因曾经有权限就永久保留读取能力。
- App：对话页提供输入、流式消息、停止、重试、数据时间提示和记录跳转。前端不直接请求模型服务。

### 数据范围与准确性

“当前用户的所有信息”指本人数据及其当前有权访问的空间内容，不包括其他成员的私人账单和私人便签。默认查询当前有效记录，历史版本与回收站须在用户明确询问时单独查询，避免把旧版本或已删除数据混入统计。

账单分析沿用当前选项：默认排除 `include_in_totals=0`、内转及已删除记录；用户可以明确要求查看排除项。聚合必须覆盖全部符合条件的记录，不能把分页样本或语义搜索命中项当作完整汇总。回答应标明时间区间、记录数及筛选规则。

重复任务要使用与客户端一致的日程、重复和完成语义；这部分当前主要在 Dart 客户端，需补充后台查询解释层并用相同样例对照验证。相对日期按照用户时区解释。

首个阶段可完整覆盖结构化字段和文字内容。图片、录音、PDF 等附件内容若也要参与语义查询，需要再加入 OCR、语音转写、文档解析或具有相应能力的模型。只有附件索引时，不能声称已理解附件内容。

只在手机离线保存、还未同步的内容，后台暂时不可见。提问前可尝试同步；失败时明确显示仅基于服务器已有数据，不应生成“已包含刚才全部修改”的误导性回答。

### 模型凭据与资料流向

API Key 留在后台配置与加密存储中，不写入 App 包或普通日志。模型只接收本次分析需要的字段和片段；这些内容会被发送到用户所配置的模型服务，需要在启用时说明。任务、便签和附件中的文本作为资料处理，不作为新的系统指令。

首版可使用现有 Java HTTP 客户端直接对接兼容 API，无须先引入复杂 Agent 框架或向量数据库。大量便签的语义检索可在实际数据规模和召回质量明确后再补充。

### 验收

1. 两个不同账号的同样问题，查询结果和引用严格隔离。
2. 账单结果与现有客户端同一批数据、同一统计口径完全一致，包括小数精度、排除汇总和内转。
3. 跨月、跨年、重复任务、逾期、软删除与历史版本的查询有可复现样例。
4. 数据超过一页时，完整汇总不漏算；无法取得的记录或附件不伪造内容。
5. 模型超时、工具失败、断流和同步失败有真实状态，恢复连接不会重复执行无界任务。
6. 模型处理期间，任务和账单同步不被长事务阻塞。

## 二、京东与淘宝个人到手价跟踪

### 先定义跟踪对象和价格

一个监控项至少要绑定：平台、本人账户、商品链接及确切 SKU、数量、收货地区和价格口径。颜色、容量、规格或数量变化不能继续当作同一个监控项比较。

建议首个试点跟踪“固定 SKU、固定数量与地区，当前账户已可享受优惠下的现金应付价”。运费、会员价、已领券、自动满减及优惠有效期需要记录。多件凑单、以旧换新、积分资产、指定银行卡或分期优惠，应单独显示条件，不能直接作为无条件价格。

优惠券集合本身可以变化，因为出现新的可用优惠也是用户关心的降价原因；同时记录条件和来源，避免混淆“可领券后的宣传价”与“当前账户已核实可享价”。不同页面、不同渠道未必给出同一价；浏览器能看到的价格也要与用户手机端核对。

### 取价渠道

| 路线 | 用途 | 本次确认程度 |
| --- | --- | --- |
| 平台正式授权接口 | 如果有覆盖本人账户、SKU 和优惠的接口，优先接入 | 尚未验证对应接口、申请资格与授权范围；不能默认通用商品接口等于本人价格 |
| 本人授权的持久浏览器会话 | 在用户登录态下读取平台实际展示的个人价格与优惠条件 | 技术上有试点路线；尚未对指定账户或商品实测，不能承诺覆盖 App 专属优惠 |
| 公开商品价、推广价或第三方历史价 | 可作为另行标注的参考 | 不能替代本人到手价，也不能在本人取价失败时无提示地回退 |
| 手机端手动核验 | 对照试点结果，处理只在 App 或特定结算条件下出现的价格 | 可作为验证依据；iPhone 的普通后台任务不能承担持续、精确定时的电商界面采集 |

如果某项优惠只有进入结算流程才显示，需要进一步确认是否存在不创建订单、且平台允许的读取方式。单纯商品页面不足以保证“最低个人到手价”。本阶段不应自动领券、加购、下单或支付；如用户日后要求这类行为，需要另外明确操作范围。

### 登录与后台运行

个人浏览器会话应在服务端或用户授权的采集机器上独立保存；浏览器环境与 App 的 WKWebView 登录态不能假定互通。推荐用户通过扫码或平台正式授权登录，不把电商密码填入 Todo 后台。

每个用户、每个平台的浏览器资料独立隔离，凭据加密保存。退出、重新授权、失效与遇到验证分别有状态；不把跳到登录页后的公开价格当作本人价格。需要验证码或重新扫码时通知用户处理，不能承诺登录后永久免维护。

采集工作交给独立后台 worker。只有平台允许访问且登录有效时才调度；从小规模、低频试点开始，例如每 30～60 分钟检查一次，再依据实际页面、限流和稳定性调整。不能承诺用户端价格变化后立即被检测到，也不通过反复请求或绕过验证来维持频率。

### 快照、判定与通知

每次成功核验保存结构化快照：监控项、账户标识、SKU、数量、地区、币种、现金应付价、价格来源、优惠条件、核验时间及必要的价格区域证据。证据截图尽量限定价格区域，避免收集无关的个人资料。

首次成功取价建立基线。之后将同一对象、同一价格口径的有效价格与上一有效价格比较，下降时记录事件。相同观察不重复通知。取价失败、商品无货、登录失效、价格解析异常不能保存成 0 元并触发“降价”。规格、数量或地区改变时重建比较基线。

降价事件与待发送通知在一个短事务内落库，实际调用 APNs 在事务外完成；重试使用稳定事件 ID，避免重复事件。多个 worker 领取任务需要租约/唯一约束，防止同一监控项重复采集和并发更新基线。具体表结构在取价试点通过后确定。

App 价格页展示最近成功核验价、时间、优惠条件、历史变化与异常状态；推送点击跳转监控项，进一步进入平台购买。通知表示“在某时刻核验到此价格”，不能保证打开时优惠仍有效。

### 远程推送的新增工作

iPhone 端启用 Push Notifications capability，向 APNs 注册并把设备 token 关联当前 Todo 账号上传；退出账号时解除关联，token 失效时更新或移除。服务端使用独立的 APNs 推送凭据发送降价通知，不能把 App Store Connect 构建分发密钥直接视为已有推送密钥。

已安装 App 且授权通知后，不需要保持 App 前台，用户可收到可见远程通知；送达与展示仍受 APNs、网络、系统和通知设置影响。服务端保存降价事件，用户打开 App 时可补看。Android 再按目标设备接入适合的远程推送通道。

Apple 官方说明：[Registering your app with APNs](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)。本次读取了其官方文档数据，确认设备 token、签名权限与 provider server 是必要环节。

### 取价试点的通过条件

1. 京东、淘宝各提供一个明确规格的商品链接，确定账户、数量、地区和需要计入的优惠条件。
2. 用户扫码/授权登录，将后台读到的价格、优惠明细与同一时刻本人手机看到的结果对照。
3. 连续取样跨越一段实际运行周期，覆盖登录失效、优惠变化、无货、页面变化及需要人工验证的状态。
4. 仅当能够说明价格来源并稳定核对个人价格后，才将该平台该类型商品接入正式监控；只取得公开价不能算通过。
5. 用可控测试快照验证降价、重复快照、错误价格、不同比较口径及推送重试，不为测试而创建真实订单。

## 建议实施顺序与待提供资料

第一步先实现 AI 只读助手。实际接入时需要模型 API 地址、模型名和 Key，并决定图片/录音等附件是否也在首版分析范围内。模型配置应通过后台配置入口提供，不放在文档或仓库里。

第二步建立京东、淘宝个人价格取价试点，需要各一条商品链接、具体规格、数量、地区，以及用户扫码授权。若一个平台暂不能取得可靠的个人价格，保留其未验证状态，不用公开价冒充。

第三步在取价路线通过后实现持久监控、历史变化和 APNs 远程推送，并完成锁屏真机通知验证。当前探索没有执行模型连通测试、电商账户登录、个人价格核对或推送发送，因此不能将这两项写成已上线功能。
